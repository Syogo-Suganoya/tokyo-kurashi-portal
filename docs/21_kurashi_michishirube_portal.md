# システム基本設計書：くらしの道しるべ（生活お悩みルーティングポータル）

## 1. システム概要

生活の困りごと（防犯・ごみ分別・AED・こども食堂・税金の使い道 等）の多くには、既に優れた公式サービスが存在する。しかし住民はその存在を知らず、たとえ辿り着いても各サービスごとにUIも粒度も異なり、「結局どこを見ればいいのか」で迷子になる。

本サービスは、**住民の困りごとにその場で答えを返す**。困りごとを自然文で入力すると、AIが分野を判定し、東京都オープンデータから構築した**簡易版コンテンツで直接回答する**。そして簡易版で賄えない要望——対応していない自治体、申請や予約が必要な手続き、より詳細な情報——に対しては、**その限界を明示した上で最適な公式サービスへ送り出す**。

### 1.1 設計思想：「答えは自前で返す。足りない分だけ公式へ送る」

```
困りごと入力
    ↓
AIが分野判定 ＋ 必要な情報を抽出
    ↓
┌─────────────────────────────┐
│ 簡易版で回答（自前・オープンデータ）        │  ← ここが本体
│  例:「ペットボトル」→ 資源ごみ / 中身を洗って  │
└─────────────────────────────┘
    ↓ 賄えない場合は限界を明示して
┌─────────────────────────────┐
│「粗大ごみの申込みはこちら」→ 区の公式受付へ     │  ← 逃げではなく設計された引き継ぎ
└─────────────────────────────┘
```

この構造には3つの利点がある。

1. **「単なるリンク集」問題が構造的に消える。** ポータル自身が答えを持つため、リンクは主役ではなく出口になる。
2. **簡易版の弱点が正直さに転化する。** 「うちのデータは令和3年度時点です、最新は公式で」と明示することは、行政情報を扱うサービスとして減点ではなく加点になる。カバー範囲を偽らない設計を最初から組み込む。
3. **カバー範囲の穴をエスカレーションが吸収する。** 対応自治体が5区しかなくても、残りは公式へ送ればサービスとして成立する。段階的に広げられる設計になり、当日の実装量をコントロールできる。

### 1.3 前方針からの変更点
当初は「既存サービスへのAIルーティング＋隙間だけ自作」という構成だったが、**全テーマで簡易版を自前で持つ**構成に転換した。これに伴い、以前の決定「地域粒度は都全域に固定」は**テーマごとの判断に変更する**（§3のTier分類を参照）。理由は、調査の結果ほとんどの生活データが区市町村単位でしか公開されていないと判明したためで、都全域に固定すると簡易版がほとんど作れなくなる。代わりに、**未対応自治体はエスカレーションリンクで公式へ送る**ことで、カバー率の低さがサービスの破綻に直結しない構造にした。

## 2. 調査結果：テーマ別のデータ入手性（実測）

東京都オープンデータカタログAPIを実際に検索し、テーマごとに「簡易版を作れるか」を判定した。**簡易版が作れるかは、そのテーマに都全域データがあるか／自治体別データのスキーマが揃っているかで決まる。**

| Tier | 意味 | 該当テーマ | 実装コスト |
| :--- | :--- | :--- | :--- |
| **A** | 都全域の一括データが存在。CSV数本で完結 | 防犯 / 学び・体験 / バリアフリー | 低 |
| **B** | 自治体別だが**国の推奨データセット標準スキーマ**に準拠。列名の揺れを吸収すれば横断統合できる | ごみ分別 | 中 |
| **C** | 自治体別かつスキーマがバラバラ。名寄せに時間がかかる | 避難所 / AED / こども食堂 / 保育所 / 公衆トイレ | 高 |
| **D** | 有用な生データが無い、または既存サービスが十分に優秀で簡易版を作る意味が薄い | 税金 / 観光 / デジタル / 社会参加 / 気候変動 | — |

### 2.2 Tier B：ごみ分別（全数調査済み・30自治体をカバー可能）

カタログAPIからごみ分別関連のCSVリソース64本を収集し、**全件を実際にダウンロードしてスキーマを検証した**。結果、**30自治体・28,088品目が即座に取り込める**ことを確認した。当初想定（数自治体）を大きく上回る。

| 区分 | 自治体 |
| :--- | :--- |
| **23区（13）** | 千代田区・中央区・港区・新宿区・文京区・墨田区・江東区・品川区・杉並区・荒川区・板橋区・葛飾区・中野区 |
| **市町村（17）** | 八王子市・立川市・武蔵野市・三鷹市・府中市・調布市・小金井市・日野市・東村山市・国分寺市・狛江市・東大和市・東久留米市・多摩市・西東京市・羽村市・瑞穂町 |

品目数上位は瑞穂町2,437 / 立川市2,082 / 多摩市1,641 / 羽村市1,618 / 府中市1,542 / 調布市1,522。**市部の方が品目数が多い**傾向があり、23区は中野区942・文京区979を除くと数百件規模。

検証結果の全量は **[`gomi_taiou_jichitai.json`](gomi_taiou_jichitai.json)** に保存済み。自治体ごとのCSV URL・エンコーディング・列マッピング・分別区分の語彙一覧が入っており、**そのまま取り込みスクリプトの設定ファイルとして使える**。

#### スキーマは2系統に収束する
| 系統 | 列構成 | 該当 |
| :--- | :--- | :--- |
| **推奨データセット系** | `全国地方公共団体コード, ID, 地方公共団体名, ゴミの品目, (カナ), 分別区分, 注意点, 粗大ごみ回収料金` | 大多数。列名に `ゴミの分別方法_` 等のプレフィックスが付く変種あり |
| **50音索引系** | `50音, 品名, 種別, 料金, 説明` | 港区・文京区 |

いずれも `品目 / 分別区分 / 注意点 / 料金` に写像できる。**列名マッピング表を1枚持てば、自治体追加が設定への数行追記で済む。** 対応自治体を増やす作業がスケールする構造であり、当日は数自治体から始めて時間が許す限り広げられる。

#### 実装上の地雷（実測で判明）

**① 世田谷区のCSVは列とデータがズレている（要注意）**
ヘッダは9列 `…品目, 分別区分, 注意点, 料金種別, 料金…` だがデータ行は7列で、しかも**品目と分別区分の中身が入れ替わっている**。

```
hdr:  …, ごみの分別方法_品目, ごみの分別方法_分別区分, …
data: 131121, 131121S00001, 不燃ごみ, アイスピック, '', 無料, ''
                            ^^^^^^^^  ^^^^^^^^^^^^
                            ここが品目列       ここが分別区分列
```
列名を信じて機械的にパースすると「品目＝不燃ごみ／分別区分＝アイスピック」という壊れたデータが787件生成される。**取り込みスクリプトに「分別区分の異なり数が行数に近ければ異常と判定して落とす」バリデーションを必ず入れる。** 世田谷区は個別に列を入れ替える特例対応とするか、対応自治体から外す。

**② 台東区のCSVは404（カタログのリンク切れ）** — カタログには2本登録されているが両方とも取得できない。対応不可。

**③ 分別区分の語彙が自治体ごとに全く違う（設計上の最重要論点）**
30自治体を通じた分別区分ラベルの異なりは**997種類**。同じ「燃えるごみ」を指すのに以下が併存する。

| 表記 | 採用自治体数 |
| :--- | :--- |
| 燃やすごみ | 11 |
| 燃やせるごみ | 9 |
| 可燃ごみ | 6 |
| 燃やさないごみ / 燃やせないごみ / 不燃ごみ | それぞれ 8 / 8 / 6 |

→ **住民に表示するラベルは、その自治体の公式表記をそのまま出す。** 勝手に「可燃ごみ」等へ正規化すると、実際のごみ袋やカレンダーの表記と食い違い、住民を混乱させる。一方でアイコン表示や横断検索のために**内部の正規化キーを別に持つ**二層構造にする。表示は公式表記、内部処理は正規化キー。この分離を型定義で強制する。

正規化キーは当初5個（`burnable` / `non_burnable` / `oversized` / `recyclable` / `not_collected`）を想定していたが、**実装時に2個足りないことが判明したため7個に拡張した**（[`src/lib/gomi/types.ts`](../src/lib/gomi/types.ts)）。

| 追加したキー | 該当例 | 5個では何が起きるか |
| :--- | :--- | :--- |
| `hazardous` | 有害ごみ / スプレー缶 / 乾電池 / 使用済蛍光管 | `non_burnable` に混ぜると**住民が危険な出し方をする** |
| `drop_off` | 使用済小型家電（拠点回収）/ 食用油（拠点回収）| 区は収集しないが拠点に持ち込めば受け付ける。`not_collected`（どこにも出せない）と同一視すると**誤情報になる** |

表示は常に公式表記なので、キーの増加はアイコンと横断検索の粒度が上がるだけで住民への見え方は変わらない。写像できないものは `other` に落とす（立川市の「せん定枝」1件のみ）。

**④ 列マッピングは「単一の列名」ではなく「候補の配列」で持つ（実装時に判明）**

[`gomi_taiou_jichitai.json`](gomi_taiou_jichitai.json) の列マッピングをそのまま信じると壊れるケースが実在した。

| 判明した事実 | 調査JSONの記述 | 影響 |
| :--- | :--- | :--- |
| 立川市の `注意点` 列は **2,082件すべて空**。実際の注意文は `備考` 列（1,147件） | `note: "注意点"` | 立川市の注意点が全て空で表示される |
| 立川市の `ゴミの品目_カナ` 列も **全件空** | 「カナ列があるのは9自治体（立川市…）」 | カナ検索が機能しない |
| 中野区の `インデックス` 列は **942件すべてひらがな** | 列マッピングに未記載 | カナ検索に使えるのに取りこぼす |

→ **候補列名を順に見て「最初に中身が入っていた列」を採用する**（[`scripts/gomi-sources.ts`](../scripts/gomi-sources.ts)）。30自治体へ広げる際にも効く一般解。

**⑤ その他**
- エンコーディングは UTF-8 BOM が19自治体、CP932 が11自治体。**判定ロジックが必須**（自治体ごとに固定してはいけない）
- 港区・文京区の `50音` 列は**頭文字1文字**であり、カナ検索には使えない。表記ゆれ吸収は自前で実装する
- 粗大ごみ料金は28自治体にあり、「アイロン台 → 粗大ごみ・100円（立川市）」まで答えられる
- 港区は1セルに複数区分が入る（例：アイロン → `粗大ごみ、不燃ごみ`）。分割して両方提示し、注意点（「最大辺が30cm以上のものは粗大ごみへ」）を併記する

### 2.3 Tier C・Dの扱い
- **Tier C** は簡易版を作らず、既存サービス（全国AEDマップ、むすびえこども食堂マップ、東京都防災アプリ等）へのエスカレーションのみとする。既存が十分に優秀で、名寄せコストに見合わない。
- **Tier D** も同様にリンクのみ。特に税金（シン・トセイ 都税収入見える化ダッシュボード）と観光（GO TOKYO、9言語＋AI翻訳121言語）は既存の完成度が高く、簡易版を作ることが劣化にしかならない。

**このTier判断そのものを画面とプレゼンに出す。** 「全テーマで無理に自作せず、データがあり横断に価値がある領域だけを自前で持ち、それ以外は優れた既存へ正直に送る」という判断は、技術的な誠実さとしてそのまま評価対象になる。

## 3. 簡易版コンテンツの詳細設計

全ての簡易版に**共通の画面契約**を持たせる。個別に作り込まず、同じ骨格に流し込むことで実装量を抑える。

```
┌────────────────────────────────┐
│ ① 答え（簡易版が返す結論）                    │
│ ② 出典・時点・カバー範囲（必ず表示）              │
│ ③ この簡易版でできないこと（明示）                │
│ ④ → 公式サービスへ（エスカレーションリンク）         │
└────────────────────────────────┘
```
②〜④を任意項目にせず**必須項目として型定義に入れる**。実装漏れがビルドエラーになり、「限界を書き忘れた画面」が存在し得なくなる。

### 3.1 ごみ分別 簡易版 `/gomi`（Tier B・デモの主役）※実装済み
- **カバー範囲**：**29自治体・27,199品目**。全数調査で取り込み可能と判定した30自治体のうち、世田谷区（列ズレ）・台東区（404）・東村山市（案内先に繋がらない）を除いた全部
- **案内先の作り方**：29自治体ぶんの公式ページURLを手で集めるのは現実的でないため、**東京都オープンデータカタログに各自治体が登録している公式ページURLを使う**。取り込み時にHTTPで疎通確認し、繋がらなければビルドを落とす。
  ただし候補には「区の花」の紹介ページのような無関係なものも混ざるので、**URLがごみ関連だと確認できたものだけを「ごみの分け方・出し方」として案内し、確認できないものは「公式サイト」と表示する**（14自治体がごみページ、15自治体が公式サイトのトップ）
- **入力**：品目名（「ペットボトル」「アイロン台」）＋自治体
- **出力**：分別区分（自治体の公式表記）・注意点・（粗大ごみなら）回収料金
- **既存に勝る点**：区の公式チャットボットは1区ずつ別サイトで、UIも操作も自治体ごとに違う。ここでは**29自治体を同一UIで引ける**。引っ越しを挟んでも、実家と自宅を比べたくても、同じ画面で完結する。またAIチャットから直接答えが返るため、サイトを探して検索し直す必要がない
- **エスカレーション**：
  - 未対応自治体（渋谷区・世田谷区・台東区）→ **なぜ対応できていないのかを書いた上で**その区市町村の公式ページへ。「渋谷区はデータを公開していない」「世田谷区は列と中身がずれており、取り込むと誤った分別区分になるためあえて対応していない」と理由まで出す
  - 粗大ごみと判定された品目 → 区の粗大ごみ受付センターへ（**申込みは簡易版では絶対にやらない**）
  - 品目が見つからない → 公式チャットボットへ
- **実装注意**：§2.2の地雷（世田谷区の列ズレ／台東区404／分別区分語彙の二層構造／エンコーディング判定／列マッピングの候補配列）を必ず踏まえる。特に**分別区分は自治体の公式表記をそのまま表示する**こと
- **列ズレ検証は実装済み**。分別区分の異なり数が行数の50%を超えたらビルドを落とす。世田谷区のCSVで実際に発火することを確認済み（165種/165行=100%で中止）

### 3.2 防犯 簡易版 `/bouhan`（Tier A）※実装済み
- **カバー範囲**：**令和6年・5,132町丁**（東京都全域）
- **入力**：町丁名または区市町村名。**入力欄を2つ持ち、2町丁を並べて比較できる**
- **出力**：罪種別内訳（凶悪犯・粗暴犯・侵入窃盗・非侵入窃盗・その他）、上位手口5件、区市町村内での順位と中央値
- **既存に勝る点**：警視庁マップ・防犯マップは地図表示が主で、「引っ越し先候補2つを数字で比べる」ことがしにくい。町丁単位の数値比較に振り切る
- **エスカレーション**：地図で面的に見たい → 東京都防犯マップ／警視庁事件事故発生マップ
- **実装注意**：CP932。**認知件数は人口・昼間人口・繁華街の有無に強く影響される。単純な件数の大小で「危ない街」と断定する表示は絶対に避ける**（繁華街を持つ町丁が必ず上位に来る）。行政データの誤読を誘発する見せ方は、審査でも実運用でも最大の減点要因になる

#### 誤読を防ぐために実装したこと（注記文言はここで確定）
- 型の側に「危険度」「治安ランク」といった**評価値を一切持たない**
- アイコンは警告色ではなく中立の📊
- **上位手口を必ず併記する。** 丸の内1丁目の418件は万引き74件・詐欺52件・その他刑法犯93件で構成され、侵入窃盗は2件。件数の多さが住民の危険を意味しないことを数字自体に語らせる
- 共通画面契約の「できないこと」に、次の3文を必ず出す（省略できない）
  - 認知件数は人口・昼間人口・繁華街の有無に強く影響されます。件数が多いことは、その町丁が危険であることを意味しません。
  - 駅や商業施設のある町丁は、そこで働く人・訪れる人の分だけ件数が増えます。住んでいる人の被害の多さとは別のものです。
  - この画面は件数を並べるだけで、治安の良し悪しを判定するものではありません。

#### このデータ特有の地雷（実装時に検証で3件検出）
1. `市区町丁` が1列に連結されている。**最初に現れる 区/市/町/村 で切ると武蔵村山市・羽村市が壊れる**。62区市町村の一覧に長い順で前方一致させる
2. 町村部だけ「西多摩郡瑞穂町大字殿ケ谷」と**郡名・島名が前置される**。単純な前方一致では町村部46町丁が丸ごと落ちた
3. 「千代田区計」を町丁名「計」として取り込むと**各区で必ず1位になる**。さらに町村部には大字を持たない実在の区域（檜原村9件）と小計の再掲（同11件）が同名で存在し、**行の順序でしか見分けられない**

→ これらを黙って通さないため、**区市町村ごとの合計をCSV自身の「○○計」行と照合し、1件でもズレたらビルドを落とす**検証を入れた。2と3はこの検証が実際に検出したもの。現在は62区市町村すべてが一致し、町丁分94,063件＋区分外689件＝CSVの合計94,752件で突合している

### 3.3 学びと体験の場 簡易版 `/manabi`（Tier A）※実装済み
- **カバー範囲**：**令和3年度・849施設 / 9種別 / 62区市町村**
- **入力**：区市町村・施設区分（9種別のチェックボックス）・キーワード
- **出力**：**1レイヤーに統合した地図**（MapLibre GL JS ＋ 国土地理院 淡色地図タイル）＋一覧
- **既存に勝る点**：施設種別ごとにサイトが分かれている現状に対し、「近くで子どもと行ける場所」を種別をまたいで一望できる。都の若者向けサービスは相談窓口（若ナビα）しかなく、この導線は存在しない
- **エスカレーション**：開館時間・休館日・イベント予約 → 都の生涯学習情報／各施設の公式サイト
- **実装注意**：CP932 / 座標系JGD2011（地図表示では実用上WGS84と同視して問題ない）/ **公開年次は令和3年度。時点を必ず画面に明示**

#### 当初想定からの変更と、このデータ特有の地雷
- **7種別ではなく9種別あった。** 女性/男女平等推進施設・生涯学習センターが加わる。全9本とも同一スキーマなので取り込みは1本の処理で読める
- 施設名の先頭の `＊` は**ゴミではなく「情報掲載サイトへのリンクがある」という意味の印**（各CSVの末尾に注記行がある）。表示からは除くが、意味のある記号だと理解した上で扱う
- 名前の途中の `?` は CP932 に変換できず落ちた文字の跡（「日比谷図書文化館??文化財事務室」）。元の文字は復元できないため空白に置き換える
- 各CSVの末尾に注記だけの行が1行ずつある（計9件）。施設として取り込まない
- **都外の施設は1件ではなく20件あった**（台東区立少年自然の家＝長野県諏訪市、渋谷区の施設＝長野県須坂市 ほか）。「近くの施設」を探す住民に黙って混ぜると行けない場所を案内することになるため、都内/都外のフラグを持ち一覧に明示する
- 座標を持たない施設が1件ある（世田谷区「まちかど図書室」＝所在地が「世田谷区内5ヶ所」）。地図に出せないだけで実在するので一覧には残し、地図に出せないことを明示する
- 都内/都外の判定を「所在地が区市町村名で始まるか」で書くと、**檜原村の郷土資料館（所在地「西多摩郡檜原村3221」）を都外と誤判定する**。§3.2 と同じ郡名前置の問題であり、判定を共通化して解決した

### 3.4 バリアフリー 簡易版 `/barrierfree`（Tier A）※実装済み
- **カバー範囲**：**6,278か所 / 3局7本**（福祉局5,969・産業労働局210・交通局99）
- **入力**：条件チェックボックス8軸（車椅子で出入りできる／中を移動できる／車椅子使用者対応トイレ／オストメイト／おむつ交換台／非常用呼び出しボタン／段差が少ない／エレベーター）＋場所の種類・区市町村・キーワード
- **出力**：条件に合う飲食店・鉄道駅・公共施設を**横断で**絞り込んだリスト＋詳細カード
- **既存に勝る点**：3つの局が別々に公開しているデータを、住民の関心事である「車椅子で行ける場所」という1軸に束ねる。**本サービスのコンセプトを最も体現する画面**
- **エスカレーション**：実際の来店可否 → 店舗・施設へ直接確認／宿泊・買い物・レジャーまで含めて探したい → 都の「だれでも東京」
- 形式は地図ではなく**条件で絞れるリスト＋詳細カード**とする。地図は `/manabi` が担当しており、画面の形式を分けることで実装時間も分散する

#### 当初想定が2つ覆った（実データ検証）
1. **「都営4線のみ」ではなくなった。** 福祉局が令和7年度に公開した鉄道駅データは**17事業者**を含む（東京地下鉄219・JR東日本157・東急78・京王73・西武57・小田急39 ほか）。**交通局の都営4線を足して計18事業者**。付録Aの未決事項「東京メトロの情報を追加できるか」はこれで解決する。
   ただし**福祉局データに東京都交通局は含まれない**ため、都営4線は交通局のデータで補う。**どちらの局も単独では都内の駅を網羅していない**という事実そのものが、この画面の存在理由になる
2. **緯度経度も持っている**（6,278か所中5,832か所）。「緯度経度が無い」のは飲食店と都営地下鉄のデータのみだった

#### 「なし」と断定しない規則は出典ごとに違う（最重要）
当初は「`〇` のみを『あり』とし、それ以外は『情報なし』」という一つの規則を想定していたが、実データは2種類あった。

| 出典 | 値 | 空欄の意味 | `×` の扱い |
| :--- | :--- | :--- | :--- |
| 産業労働局（飲食店）・交通局（都営） | `〇` と空欄の**2値** | 未記入 | （存在しない） |
| 福祉局（鉄道駅・公共施設） | `○` `×` 空欄の**3値** | 未記入 | 明示的な「なし」 |

**片方の規則を他方に当てると、どちらの向きにも実害が出る。**
- 2値の規則を福祉局データに当てる → 「介助用ベッドは無い」という当事者に必要な情報が消える
- 3値の規則を飲食店データに当てる → 実際には入れる店を「入れない」と表示し、当事者を排除する

→ 取り込み側で吸収し、画面は `yes` / `no` / `unknown` の3値だけを見る。**飲食店データから `no` が生成されていないことをビルド時に検証している**。

#### その他の実装注意
- 駅名に路線コードが埋め込まれている（`（A-01）西馬込`）ためパースが必要
- 福祉局のデータはトイレ1つが1行なので、1つの駅・施設が複数行になる。場所を単位にまとめ、設備は「どれか1つでも yes なら yes」で統合する
- **条件で絞ると残るのは「その条件があると明記されている場所」だけ**で、漏れた場所の多くは未記入。この違いを画面上部と「できないこと」の両方で必ず伝える

## 4. AI設計：分野判定から「ツール選択＋情報抽出」へ

簡易版が答えを返す構成になったため、AIの役割が変わる。以前は「どの外部サービスへ送るか」の分類タスクだったが、今は**どの簡易版をどんなパラメータで呼ぶか**を決めるタスクになる。Gemini API の **function calling** をそのまま使う。

### 4.1 各簡易版を1つのツールとして定義する
```jsonc
// 例
{ "name": "search_gomi",       "input": { "item": "ペットボトル", "municipality": "立川市" } }
{ "name": "search_bouhan",     "input": { "area": "西新宿７丁目" } }
{ "name": "search_manabi",     "input": { "municipality": "中野区", "kinds": ["図書館"] } }
{ "name": "search_barrierfree","input": { "features": ["wheelchair_entry", "accessible_toilet"], "category": "restaurant" } }
{ "name": "no_tool",           "input": { "topic": "kenko" } }  // 簡易版で扱えない分野
```

**AIの出力は必ずこちらの型に絞り込む**（[`src/lib/ai/route-query.ts`](../src/lib/ai/route-query.ts)）。知らないツール名・知らない施設区分・知らない設備キーは捨てる。AIの出力をそのまま信用しない。

### 4.2 最重要の設計判断：LLMに答えとURLを生成させない
- **答えの本文はLLMが作らない。** ツールの戻り値（オープンデータそのもの）を画面に出す。LLMがやるのは「どのツールを呼ぶか」「入力文から品目名・地名を抜き出すか」だけ。**分別区分や犯罪件数をLLMが創作する経路が存在しない。**
- **URLもLLMが生成しない。** エスカレーション先はキュレーションDBに実在するIDでのみ参照する。`no_tool` が返せるのも**閉じた分野の列挙値だけ**で、そこからIDへサーバ側で写像する。LLMが生成した文字列がリンク先になる経路は存在せず、存在しない行政URLの提示が構造的に起こり得ない。
- **どの経路で判定したかを画面に出す。** Gemini が答えたのか、フォールバックのキーワード判定が答えたのかを毎回表示する。AIが落ちていることを隠さない。

これは実装詳細ではなく主張材料として扱う。提出フォーム3-2「何をAIにさせ、何を人が担保したか」への回答がそのままこれになる。**行政情報を扱うサービスとして、AIに答えさせない部分をどこに引いたかが設計の核心である。**

### 4.3 パラメータが足りないときの聞き返し
ごみ分別は自治体が特定できないと答えられない。`municipality` が抽出できなかった場合、推測で答えず**1問だけ聞き返す**（「どちらの区市町村にお住まいですか？」）。一度答えたらセッション中は保持し、以降のごみ分別質問では聞き返さない。

### 4.4 該当なし・障害時
- どの簡易版でも扱えない分野（Tier C・D）→ `no_tool` を返し、キュレーションDBから既存サービスのリンクカードを提示する。**この経路が従来の「リンク集」機能そのものであり、機能として残っている**
- **§10 の12テーマすべてに `no_tool` の受け皿を用意する。** 受け皿の無い分野は `other` に落ちて汎用の横断検索へ流れてしまい、住民から見れば「答えてくれない」のと変わらない。自前の簡易版を持たない分野こそ、担当している既存サービスへ正確に送ることに価値がある
  （分野キー：`bousai` `bouhan` `kenko` `kikou` `seikatsu` `zeikin` `shakai` `kodomo` `fukushi` `digital` `kotsu` `kanko` `other`）
- LLM API障害時 → キーワード部分一致で簡易版へ直接ルーティングするフォールバックに切り替える。デモ当日にAPIが不調でも画面が死なない保険

## 5. エスカレーションの型（設計の要）

リンクを「答えられなかったときの逃げ」ではなく**設計された引き継ぎ**にするため、発火理由を4種類に類型化し、画面上でも理由を明示する。

| 型 | 発火条件 | 文言例 |
| :--- | :--- | :--- |
| **範囲外** | 未対応の自治体・路線・施設種別 | 「渋谷区はまだ対応していません。区の公式ページで調べられます」 |
| **鮮度** | データの公開時点が古い可能性 | 「令和3年度時点の情報です。最新は施設の公式サイトでご確認ください」 |
| **手続き** | 申請・予約・相談が必要 | 「粗大ごみの申込みは区の受付センターで行えます」 |
| **深掘り** | より詳細・地図・リアルタイム情報 | 「地図で周辺一帯を見たい方は防犯マップへ」 |

**「手続き」型は特に重要。** 簡易版は「知る」までを担い、申請・予約・相談といった**住民に責任が発生する行為は絶対に代行せず、必ず公式へ送る。** この線引きを設計段階で明文化しておくことは、社会実装の可能性を問う審査項目に対する直接の回答になる。

## 6. 画面遷移・UX設計 ※実装済み

**ランディング（`/`）とチャット（`/chat`）を分ける。** トップは「何ができるか」を伝える場所、
`/chat` は「実際に聞く」場所と役割を分けた。トップにも入力欄は置くが、送信すると
`/chat?q=...` へ移り、その質問を投げた状態で開く。トップに答えが積み上がっていくと、
初めて来た人が何のサービスか分からないまま画面が埋まるためである。

### 6.1 トップページ（`/`）
読み手は**ハッカソンの審査員ではなく、困りごとを抱えた住民**として書く。
「テーマ」「Tier」のような作り手の言葉は画面に出さない。

1. **主張**：見出しは「AIは、答えを書きません。」。続けて**答えがどこから来るかの図**を置く。
   図では **AIを箱ではなく矢印として描く**（答えが入っている箱は行政のオープンデータと
   公式サービスだけになり、AIが答えを作らないことが図の構造そのもので伝わる）。図の手前に入力欄
2. **こんなことが聞けます**（`#examples`）：**分野の分類ではなく住民が実際に口にする言葉**で
   12ほど例を並べる。「これ、燃えるごみ？」「つらいとき、どこに相談すればいい？」のように書き、
   その場で答えるものと公式サービスへ案内するものを混ぜて置く。
   **どちらであっても行き先があること**が伝わればよい。
   分野を12に分けたことは内部の整理であって、住民に見せる情報ではない
3. **その場でお答えする4つ**（`#tools`）：`/gomi` `/bouhan` `/manabi` `/barrierfree` へのカード。
   分野の色帯・図記号・実データから出した件数を持つ。
   なぜこの4つだけ自前なのかは「データが揃っていて、ばらばらのままだと探しにくいから」と平易に書く
4. **対比**（`#compare`）：よくあるAIチャット（検索して要約させる作り）との違いを5点で並べる
5. **ご案内先**（`#links`）：キュレーションDBの全件。「人が確認した一覧しか使わない」ことが件数で見える

### 6.2 チャット（`/chat`）
自然文入力。結果は§3の共通契約でカード表示。`?q=` が付いていればその質問を投げた状態で開く。

### 6.3 見た目の方針
見た目の下敷きは**街の案内標識**。サービス名が「道しるべ」であり、機能の中心も「どこへ送るか」なので、案内板の語彙（濃い藍の地・太い矢印・分野ごとの色帯・等幅の数字）をそのまま設計言語にした。**色は装飾ではなく分野を見分けるための印**として使う。和文は `word-break: auto-phrase` で文節折り返しにする。

## 8. デモシナリオ（2分プレゼン想定）

1. **簡易版が答える**：「ペットボトルってどう捨てるの？」→ 区市町村を1問聞き返し → 立川市を選ぶと **その場で「ペットボトル／水ですすぐ」と回答**（立川市の公式表記そのまま）。既存はチャットボットのあるサイトを探すところから始まる。
2. **エスカレーションが働く**：「アイロン台を捨てたい」→ 粗大ごみと判定 → 立川市は **料金100円まで答えた上で**「申込みは受付センターへ」と公式リンク。手続きは代行しないという線引きを見せる。
   **同じ品目を中野区で引くと料金は答えず**、「中野区のオープンデータには粗大ごみの料金が含まれていないため、料金はお答えできません」と限界を出す。**同一UIで自治体差がそのまま見える**ことと、答えられないことを隠さない設計が一度に伝わる。続けて渋谷区を選び、範囲外エスカレーションも見せる。
3. **横断の価値**：「車椅子で行ける店や駅を知りたい」→ `/barrierfree`。3局にバラバラだったデータ6,278か所が1画面で絞り込めることを示す。**福祉局のデータには都営地下鉄が含まれず、交通局のデータには他社が含まれない**という事実を出せば、「どちらの局も単独では都内の駅を網羅していない」＝この画面の存在理由が一言で伝わる。
   併せて `○`／`×`／`—（情報なし）` の3値表示を見せる。「なし」と書かれていない限り「なし」とは表示しないという方針が、当事者を排除しないための設計であることを説明する。
4. **締め**：Tier表と、トップページの「AIは、答えを書きません。」＋答えの経路図。
   「データがあり横断に価値がある領域だけ自前で持ち、既存が優れている領域には正直に送る」という判断と、**AIを箱ではなく矢印として設計した**という一点を提示して終わる。

## 11. 競合調査メモ

### 生活ガイド.com（https://www.seikatsu-guide.com/）
- 全国の市区町村の**行政データ＋住民口コミ**を集約したプラットフォーム。23区・全国市ごとに200項目以上の行政データを閲覧でき、2自治体間の比較機能を持つ
- カバー領域は補助金・住宅・子育て・医療・介護保険料・治安・待機児童・ふるさと納税・ハザードマップ・水道料金など広範。法人向けにレポート作成ツール・行政データ販売も展開
- **相違点**：粒度が「行政サービスの有無・数値」であり、**住民の具体的な困りごとに答えを返すものではない**。「ペットボトルをどう捨てるか」には答えられない。本サービスは自治体の比較ではなく、目の前の困りごとの解決に振り切る

### Tokyo支援ナビ（https://www.support-navi.metro.tokyo.lg.jp/）
- 東京都自身が運営する支援情報の横断検索サイトで、デジタルテーマ課題「分野横断的な情報検索システム」に最も近い既存サービス
- ただし**制度・窓口の検索**が主で、対象も都自身が実施するものが中心。区市町村独自のサービスや民間・NPOまでは横断していない
- 本サービスは**検索結果ではなく答えを返す**点、および区市町村・民間・NPOまで対象を広げる点で差別化する

### 生成AIチャットボット全般（RAG構成）
機能の見た目としては「チャットで質問すると行政情報が返る」であり、資料を検索してLLMに要約させる作り（RAG）と混同されやすい。**差別化の核心は、LLMに任せる範囲をどこで切ったかにある。**

| | RAG構成のAIチャット | 本サービス |
| :--- | :--- | :--- |
| 答えの文章 | LLMが書く。もっともらしい誤りが混ざりうる | **書かない。** オープンデータの値をそのまま出す |
| 出典 | 文章の後ろに参考リンクが付く程度 | 出典・時点・カバー範囲を**型で必須化**して必ず表示 |
| 案内するURL | LLMが生成し、存在しないURLが混ざりうる | 人が確認した一覧に**実在するIDでしか参照できない** |
| 答えられないとき | 推測で埋めるか、曖昧に濁す | できないことを書き、担当する公式へ送る（**空にできない型**） |
| LLMが止まったとき | 何も答えられなくなる | キーワード判定に切り替えて動き続ける |

この対比はトップページ（`#compare`）にそのまま掲載している。**行政情報を扱うサービスとして、どこまでをAIに任せないと決めたかが、そのまま差別化になる。**

### 総合判断
- 前方針で最大リスクだった「単なるリンク集に見える」問題は、簡易版が答えを持つ構成により**構造的に解消された**
- 次のリスクだった「よくあるAIチャットに見える」問題は、**LLMに文章もURLも生成させない**構成と、それを図と対比表で明示することで解消する
- 残る最大リスクは**簡易版の品質**。中途半端な自作は「公式より劣るものを作った」という評価になる。これを防ぐのが§3の共通画面契約（限界の明示）と§5のエスカレーション類型であり、**「劣っている部分を隠さず公式へ送る」ことで、簡易版が公式の劣化版ではなく入口として位置づけられる**
